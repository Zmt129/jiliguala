## 1. 命名规范：别让人猜你的表是干嘛的

### ❌ 错误示范

```sql
-- 这是什么表？完全看不懂！
CREATE TABLE t1 (
    id INT,
    f1 VARCHAR(50),
    f2 INT,
    f3 DATETIME
);

-- 缩写让人崩溃
CREATE TABLE usr_ord_rel (
    u_id INT,      -- 这是用户 ID 还是订单 ID？
    o_id INT,
    crt_tm DATETIME  -- create time? 谁能看懂？
);
```

**问题：**
- 新人来了根本看不懂
- 三个月后你自己也忘了
- 跨团队协作时沟通成本极高

### ✅ 正确做法

#### 表命名规则

```sql
-- 规则 1：使用有意义的英文单词，复数形式
CREATE TABLE users (           -- ✅ 用户表
CREATE TABLE orders (          -- ✅ 订单表
CREATE TABLE order_items (     -- ✅ 订单项表

-- 规则 2：关联表用"表名_表名"或"主表_from_to"格式
CREATE TABLE user_roles (      -- ✅ 用户角色关联表
CREATE TABLE role_permissions (-- ✅ 角色权限关联表

-- 规则 3：配置表、字典表加后缀
CREATE TABLE system_config (   -- ✅ 系统配置表
CREATE TABLE dict_order_status -- ✅ 订单状态字典表
```

#### 字段命名规则

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY COMMENT '用户 ID',
    
    -- 基础信息用简单名词
    username VARCHAR(50) COMMENT '用户名',
    email VARCHAR(100) COMMENT '邮箱',
    phone VARCHAR(20) COMMENT '手机号',
    
    -- 时间统一用 xxx_at 结尾
    created_at DATETIME COMMENT '创建时间',
    updated_at DATETIME COMMENT '更新时间',
    deleted_at DATETIME COMMENT '删除时间',
    
    -- 状态用 status，类型用 type
    status TINYINT COMMENT '状态：0-禁用 1-启用',
    user_type TINYINT COMMENT '用户类型：1-普通 2-VIP 3-企业',
    
    -- 外键用"关联表名_单数_id"
    department_id BIGINT COMMENT '部门 ID（关联 departments 表）',
    manager_id BIGINT COMMENT '上级 ID（关联 users 表）'
);
```

### 💡 核心原则

**三不要：**
1. 不要用拼音（yonghu、dingdan）
2. 不要用无意义缩写（u_info、o_stat）
3. 不要用保留字（user、order、group）

**三要：**
1. 要用英文复数（users、orders）
2. 要见名知意（created_at、status）
3. 要统一风格（全大写、全小写或驼峰）

## 2. 字段设计：细节决定成败

### ⚠️ 常见错误

#### 错误 1：所有字符串都用 VARCHAR(255)

```sql
-- ❌ 错误示范
CREATE TABLE users (
    username VARCHAR(255),  -- 用户名需要 255 吗？
    phone VARCHAR(255),     -- 手机号要 255？
    status VARCHAR(255)     -- 状态也要 255？
);
```

**问题：**
- 浪费存储空间
- 影响索引效率
- 数据质量难以保证

#### 错误 2：金额用 FLOAT/DOUBLE

```sql
-- ❌ 错误示范
CREATE TABLE orders (
    amount FLOAT(10,2)  -- 浮点数会有精度丢失！
);

-- 计算结果可能让你崩溃
SELECT 0.1 + 0.2;  -- 结果：0.30000000000000004
```

#### 错误 3：时间都用 VARCHAR

```sql
-- ❌ 错误示范
CREATE TABLE orders (
    create_time VARCHAR(20)  -- "2024-01-01 12:00:00"
);
```

**问题：**
- 无法进行时区转换
- 日期计算困难
- 排序性能差

### ✅ 正确做法

#### 合理设置字段长度

```sql
CREATE TABLE users (
    -- 根据实际需求设置
    username VARCHAR(50) COMMENT '用户名（最多 50 字符）',
    password_hash VARCHAR(255) COMMENT '密码哈希（BCrypt 固定 60 字符）',
    email VARCHAR(100) COMMENT '邮箱（标准不超过 100）',
    phone VARCHAR(20) COMMENT '手机号（+86 这种格式）',
    real_name VARCHAR(50) COMMENT '真实姓名',
    id_card VARCHAR(18) COMMENT '身份证号（固定 18 位）',
    
    -- 长文本用 TEXT
    address TEXT COMMENT '详细地址',
    remark TEXT COMMENT '备注'
);
```

#### 金额用 DECIMAL

```sql
CREATE TABLE orders (
    -- ✅ 正确：DECIMAL 精确计算
    amount DECIMAL(10,2) COMMENT '订单金额',
    total_amount DECIMAL(12,2) COMMENT '总金额',
    discount_amount DECIMAL(10,2) COMMENT '优惠金额',
    paid_amount DECIMAL(10,2) COMMENT '已付金额'
);

-- 高精度场景（如汇率、利率）
CREATE TABLE exchange_rate (
    rate DECIMAL(18,6) COMMENT '汇率（精确到小数点后 6 位）',
    interest_rate DECIMAL(5,4) COMMENT '利率（如 0.0525 表示 5.25%）'
);
```

#### 时间用 DATETIME/TIMESTAMP

```sql
CREATE TABLE orders (
    -- ✅ 推荐：DATETIME（与时区无关）
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    
    -- TIMESTAMP 适合记录行版本（自动更新）
    row_version TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    
    -- 业务时间
    order_time DATETIME NOT NULL COMMENT '下单时间',
    pay_time DATETIME COMMENT '支付时间',
    ship_time DATETIME COMMENT '发货时间',
    
    -- 只存储日期（不存储时间）
    birthday DATE COMMENT '生日',
    register_date DATE COMMENT '注册日期'
);
```

### 📊 常用字段类型选择

| 场景 | 推荐类型 | 说明 |
|------|---------|------|
| 主键 | BIGINT | 自增或雪花算法 |
| 金额 | DECIMAL(10,2) | 精确计算 |
| 手机号 | VARCHAR(20) | 支持国际号码 |
| 邮箱 | VARCHAR(100) | 标准邮箱长度 |
| 状态 | TINYINT | 0/1/2 足够 |
| 类型 | TINYINT | 枚举类型 |
| 短文本 | VARCHAR(n) | 根据实际设置 |
| 长文本 | TEXT | 文章、描述 |
| 时间 | DATETIME | 业务时间 |
| 开关 | TINYINT(1) | 0/1 |
| 百分比 | DECIMAL(5,4) | 0.0000-1.0000 |

## 3. 索引设计：不是越多越好

### ❌ 错误示范

#### 错误 1：不给任何索引

```sql
-- ❌ 错误：查询全表扫描
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT,      -- 没索引，查询慢
    order_no VARCHAR(50),-- 没索引，查询慢
    status TINYINT       -- 没索引，查询慢
);

-- 这样的查询会哭
SELECT * FROM orders WHERE user_id = 123;
SELECT * FROM orders WHERE order_no = 'ORD20240101001';
```

#### 错误 2：滥用索引

```sql
-- ❌ 错误：给所有字段都加索引
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    username VARCHAR(50),
    email VARCHAR(100),
    phone VARCHAR(20),
    status TINYINT,
    created_at DATETIME,
    updated_at DATETIME,
    
    INDEX idx_username (username),
    INDEX idx_email (email),
    INDEX idx_phone (phone),
    INDEX idx_status (status),
    INDEX idx_created_at (created_at),
    INDEX idx_updated_at (updated_at)
    -- 6 个索引！写入性能爆炸
);
```

**问题：**
- 每个索引都占用磁盘空间
- INSERT/UPDATE/DELETE 时要更新所有索引
- 写操作性能下降 5-10 倍

#### 错误 3：索引失效的场景

```sql
-- 有索引但没用
CREATE TABLE users (
    username VARCHAR(50),
    INDEX idx_username (username)
);

-- 以下查询不会用索引：
SELECT * FROM users WHERE LOWER(username) = 'admin';  -- 函数操作
SELECT * FROM users WHERE username LIKE '%admin%';    -- 左模糊
SELECT * FROM users WHERE username != 'admin';        -- 否定条件
SELECT * FROM users WHERE username = 'admin' OR email = 'a@b.com'; -- OR 条件
```

### ✅ 正确做法

#### 合理创建索引

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    order_no VARCHAR(50) NOT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(10,2),
    created_at DATETIME,
    
    -- 单列索引：高频查询字段
    INDEX idx_user_id (user_id),
    UNIQUE INDEX idx_order_no (order_no),  -- 唯一索引
    
    -- 联合索引：多个字段组合查询
    INDEX idx_user_status (user_id, status),  -- 查用户订单状态
    INDEX idx_status_created (status, created_at)  -- 按状态和时间筛选
    
    -- 注意：联合索引遵循最左前缀原则
    -- idx_user_status 可以用于：
    -- WHERE user_id = ?                    ✅
    -- WHERE user_id = ? AND status = ?     ✅
    -- WHERE status = ?                     ❌
);
```

#### 索引设计原则

**什么字段适合建索引？**

✅ **应该建索引的：**
- 主键、外键
- 高频查询的 WHERE 条件字段
- ORDER BY、GROUP BY 字段
- DISTINCT 去重字段
- 联合查询的连接字段

❌ **不应该建索引的：**
- 表记录太少（< 1000 条）
- 频繁更新的字段
- 区分度低的字段（如性别）
- 只有 YES/NO 的字段
- 很少在查询中使用的字段

#### 覆盖索引优化

```sql
-- 原始查询（需要回表）
SELECT user_id, status FROM orders WHERE user_id = 123;

-- 使用覆盖索引（不需要回表，更快）
CREATE INDEX idx_user_status_include (user_id, status);

-- 或者这样写（利用覆盖索引）
SELECT /*+ INDEX(orders idx_user_status) */ 
    user_id, status 
FROM orders 
WHERE user_id = 123;
```

### 📊 索引性能对比

```sql
-- 100 万条数据的 orders 表

-- 无索引：全表扫描
SELECT * FROM orders WHERE user_id = 123;
-- 耗时：约 500ms

-- 有索引：B+ 树查找
CREATE INDEX idx_user_id ON orders(user_id);
SELECT * FROM orders WHERE user_id = 123;
-- 耗时：约 5ms（快 100 倍！）

-- 覆盖索引：不需要回表
SELECT id, user_id FROM orders WHERE user_id = 123;
-- 耗时：约 1ms（再快 5 倍！）
```

## 4. 数据类型：合适的才是最好的

### 🎯 常见类型选择误区

#### 误区 1：整数都用 INT

```sql
-- ❌ 错误
CREATE TABLE users (
    id INT,              -- 用户超过 21 亿怎么办？
    phone INT            -- 手机号以 0 开头就废了
);

-- ✅ 正确
CREATE TABLE users (
    id BIGINT,           -- 最大 922 亿亿，够用
    phone VARCHAR(20)    -- 支持 +86、空格等
);
```

**整数类型范围：**

| 类型 | 字节 | 范围 | 适用场景 |
|------|------|------|---------|
| TINYINT | 1 | -128 ~ 127 | 状态、标志位 |
| SMALLINT | 2 | -32768 ~ 32767 | 小计数 |
| MEDIUMINT | 3 | -8388608 ~ 8388607 | 中等数量 |
| INT | 4 | -21 亿 ~ 21 亿 | 一般计数 |
| BIGINT | 8 | ±922 亿亿 | 主键、大数量 |

#### 误区 2：CHAR 和 VARCHAR 乱用

```sql
-- ❌ 错误
CREATE TABLE users (
    id_card CHAR(18),      -- 有些人是 X 结尾
    phone CHAR(11),        -- 国际号码不止 11 位
    username VARCHAR(5)    -- 5 个字符不够啊
);

-- ✅ 正确
CREATE TABLE users (
    id_card VARCHAR(18),   -- 可能有 X
    phone VARCHAR(20),     -- 支持国际号码
    username VARCHAR(50)   -- 留有余地
);
```

**CHAR vs VARCHAR：**

| 特性 | CHAR | VARCHAR |
|------|------|---------|
| 长度 | 固定 | 可变 |
| 存储 | 右补空格 | 不补空格 |
| 性能 | 略快 | 略慢 |
| 适用 | 身份证、MD5 | 大部分场景 |

#### 误区 3：TEXT 类型滥用

```sql
-- ❌ 错误
CREATE TABLE articles (
    title TEXT,            -- 标题用 TEXT？
    summary TEXT           -- 摘要也用 TEXT？
);

-- ✅ 正确
CREATE TABLE articles (
    title VARCHAR(200),    -- 标题一般不超过 200
    summary VARCHAR(500),  -- 摘要 500 够了
    content TEXT           -- 正文用 TEXT
);
```

**TEXT 类型注意事项：**
- TEXT 不能有默认值
- TEXT 查询性能较差
- TEXT 不适合建索引（可以前缀索引）
- 大量 TEXT 会影响缓存效率

### 💡 类型选择速查表

```sql
CREATE TABLE example (
    -- 主键
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    
    -- 金额相关
    price DECIMAL(10,2),       -- 价格
    amount DECIMAL(12,2),      -- 金额
    quantity INT,              -- 数量
    discount DECIMAL(4,2),     -- 折扣（0.00-9.99）
    
    -- 状态相关
    status TINYINT DEFAULT 1,  -- 状态：0-禁用 1-启用
    type TINYINT,              -- 类型：1-A 2-B 3-C
    is_deleted TINYINT(1) DEFAULT 0,  -- 逻辑删除
    
    -- 字符串
    code VARCHAR(50),          -- 编码
    name VARCHAR(100),         -- 名称
    description VARCHAR(500),  -- 描述
    content TEXT,              -- 内容
    
    -- 时间
    birth_date DATE,           -- 出生日期
    start_time DATETIME,       -- 开始时间
    end_time DATETIME,         -- 结束时间
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    
    -- 特殊类型
    json_data JSON,            -- JSON 数据
    blob_data LONGBLOB         -- 二进制数据
);
```

## 5. 约束和规范：没有规矩不成方圆

### 🔒 必要的约束

#### NOT NULL 约束

```sql
-- ❌ 错误：允许 NULL 导致很多麻烦
CREATE TABLE users (
    username VARCHAR(50),      -- 可以为 NULL？
    email VARCHAR(100),        -- 可以为 NULL？
    status TINYINT             -- 可以为 NULL？
);

-- ✅ 正确：明确哪些字段不能为空
CREATE TABLE users (
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    status TINYINT NOT NULL DEFAULT 1,
    phone VARCHAR(20)          -- 这个可以为空
);
```

**NULL 值的危害：**
- COUNT() 统计不准确
- 比较运算结果为 NULL
- 索引效率降低
- 代码中要多做判断

#### DEFAULT 默认值

```sql
CREATE TABLE users (
    -- 数值型默认值
    status TINYINT NOT NULL DEFAULT 1,
    is_vip TINYINT(1) NOT NULL DEFAULT 0,
    balance DECIMAL(10,2) NOT NULL DEFAULT 0.00,
    
    -- 字符串默认值
    gender TINYINT NOT NULL DEFAULT 0 COMMENT '0-未知 1-男 2-女',
    avatar VARCHAR(255) NOT NULL DEFAULT '' COMMENT '头像 URL',
    
    -- 时间默认值
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

#### UNIQUE 唯一约束

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    phone VARCHAR(20),
    
    -- 唯一约束
    UNIQUE INDEX uk_username (username),
    UNIQUE INDEX uk_email (email),
    UNIQUE INDEX uk_phone (phone)
);

-- 插入重复数据会报错
INSERT INTO users (username) VALUES ('admin');  -- ✅
INSERT INTO users (username) VALUES ('admin');  -- ❌ Duplicate entry
```

#### FOREIGN KEY 外键约束

**观点分歧：**

✅ **支持外键派：**
- 保证数据一致性
- 级联删除很方便
- 数据库层面保证

❌ **反对外键派：**
- 影响性能
- 分布式不支持
- 应用层控制更灵活

**折中方案：**

```sql
-- 物理外键（小项目可用）
CREATE TABLE orders (
    user_id BIGINT NOT NULL,
    CONSTRAINT fk_orders_user 
        FOREIGN KEY (user_id) REFERENCES users(id)
        ON DELETE CASCADE  -- 用户删除，订单级联删除
        ON UPDATE CASCADE
);

-- 逻辑外键（推荐，应用层控制）
CREATE TABLE orders (
    user_id BIGINT NOT NULL COMMENT '用户 ID（关联 users.id）',
    INDEX idx_user_id (user_id)
    -- 不加 FOREIGN KEY 约束
);

-- 在代码中控制
public void deleteUser(Long userId) {
    // 先删除关联数据
    orderRepository.deleteByUserId(userId);
    // 再删除用户
    userRepository.deleteById(userId);
}
```

### 📝 注释规范

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '用户 ID，主键自增',
    
    -- 基础信息
    username VARCHAR(50) NOT NULL COMMENT '用户名，登录用',
    password_hash VARCHAR(255) NOT NULL COMMENT '密码哈希（BCrypt）',
    nickname VARCHAR(50) COMMENT '昵称，显示用',
    
    -- 联系信息
    email VARCHAR(100) NOT NULL COMMENT '邮箱',
    phone VARCHAR(20) COMMENT '手机号',
    
    -- 状态信息
    status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：0-禁用 1-启用 2-冻结',
    user_type TINYINT NOT NULL DEFAULT 1 COMMENT '用户类型：1-普通 2-VIP 3-企业',
    
    -- 时间信息
    last_login_at DATETIME COMMENT '最后登录时间',
    last_login_ip VARCHAR(50) COMMENT '最后登录 IP',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    deleted_at DATETIME COMMENT '删除时间（软删除）',
    
    -- 索引
    INDEX idx_username (username),
    INDEX idx_email (email),
    INDEX idx_phone (phone),
    INDEX idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

**注释要点：**
- 每个字段都要有注释
- 说明字段的用途
- 枚举值要说明含义
- 默认值要说明

## 6. 扩展性设计：为未来留条路

### 🚀 预留扩展字段

#### 方法 1：预留字段（简单直接）

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    username VARCHAR(50),
    
    -- 预留扩展字段
    ext_field1 VARCHAR(100) COMMENT '扩展字段 1',
    ext_field2 VARCHAR(100) COMMENT '扩展字段 2',
    ext_field3 INT COMMENT '扩展字段 3',
    ext_field4 DATETIME COMMENT '扩展字段 4',
    
    -- 或者统一用一个 JSON
    ext_data JSON COMMENT '扩展数据'
);
```

**优点：** 简单，修改方便  
**缺点：** 字段数量有限，语义不明确

#### 方法 2：JSON 扩展（推荐）

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    username VARCHAR(50),
    email VARCHAR(100),
    
    -- JSON 存储扩展信息
    extra_info JSON COMMENT '扩展信息',
    
    -- 示例数据：
    -- {
    --   "wechat": "wx123456",
    --   "birthday": "1990-01-01",
    --   "interests": ["reading", "coding"],
    --   "settings": {
    --     "notification": true,
    --     "theme": "dark"
    --   }
    -- }
);

-- 查询 JSON 字段
SELECT * FROM users 
WHERE JSON_EXTRACT(extra_info, '$.wechat') = 'wx123456';

-- 更新 JSON 字段
UPDATE users 
SET JSON_SET(extra_info, '$.wechat', 'wx789') 
WHERE id = 1;
```

**优点：** 灵活，可以随时添加字段  
**缺点：** 查询性能稍差，无法建索引（MySQL 5.7+ 可以虚拟列索引）

#### 方法 3：扩展表（正规方案）

```sql
-- 主表：存储核心字段
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    username VARCHAR(50),
    email VARCHAR(100),
    created_at DATETIME
);

-- 扩展表：存储详细信息
CREATE TABLE user_profiles (
    user_id BIGINT PRIMARY KEY,
    real_name VARCHAR(50),
    birthday DATE,
    gender TINYINT,
    address TEXT,
    company VARCHAR(100),
    position VARCHAR(50),
    
    FOREIGN KEY (user_id) REFERENCES users(id)
);

-- 设置表：存储用户配置
CREATE TABLE user_settings (
    user_id BIGINT PRIMARY KEY,
    notification_enabled TINYINT(1) DEFAULT 1,
    theme VARCHAR(20) DEFAULT 'light',
    language VARCHAR(10) DEFAULT 'zh-CN',
    
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

**优点：** 结构清晰，性能好  
**缺点：** 需要 JOIN 查询

## 7. 实战案例：从错误到正确

### 📦 案例 1：用户表设计演进

#### V1.0（初版）

```sql
-- ❌ 问题很多
CREATE TABLE user (
    id INT PRIMARY KEY,
    name VARCHAR(255),
    pwd VARCHAR(255),
    tel VARCHAR(255),
    info TEXT
);
```

**问题清单：**
- 表名用单数
- 字段名不规范（name、pwd）
- 所有 VARCHAR 都是 255
- 密码明文存储
- 没有时间字段
- 没有状态字段
- 没有索引

#### V2.0（改进版）

```sql
-- ✅ 好多了
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    password VARCHAR(255) NOT NULL,
    email VARCHAR(100),
    phone VARCHAR(20),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    
    INDEX idx_username (username)
);
```

**改进点：**
- 表名复数
- 字段规范
- 添加时间
- 添加索引

#### V3.0（最终版）

```sql
-- ✅ 生产级别
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '用户 ID',
    username VARCHAR(50) NOT NULL COMMENT '用户名',
    password_hash VARCHAR(255) NOT NULL COMMENT '密码哈希（BCrypt）',
    email VARCHAR(100) NOT NULL COMMENT '邮箱',
    phone VARCHAR(20) COMMENT '手机号',
    nickname VARCHAR(50) COMMENT '昵称',
    avatar VARCHAR(255) DEFAULT '' COMMENT '头像',
    status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：0-禁用 1-启用',
    last_login_at DATETIME COMMENT '最后登录时间',
    last_login_ip VARCHAR(50) COMMENT '最后登录 IP',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    deleted_at DATETIME COMMENT '删除时间',
    
    UNIQUE INDEX uk_username (username),
    UNIQUE INDEX uk_email (email),
    INDEX idx_phone (phone),
    INDEX idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

### 🛒 案例 2：电商订单表

```sql
-- ✅ 完整的订单表设计
CREATE TABLE orders (
    -- 主键
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '订单 ID',
    
    -- 订单基本信息
    order_no VARCHAR(50) NOT NULL COMMENT '订单编号（唯一）',
    user_id BIGINT NOT NULL COMMENT '用户 ID',
    
    -- 金额信息
    total_amount DECIMAL(12,2) NOT NULL DEFAULT 0.00 COMMENT '商品总金额',
    freight_amount DECIMAL(10,2) NOT NULL DEFAULT 0.00 COMMENT '运费',
    discount_amount DECIMAL(10,2) NOT NULL DEFAULT 0.00 COMMENT '优惠金额',
    paid_amount DECIMAL(12,2) NOT NULL DEFAULT 0.00 COMMENT '实付金额',
    
    -- 订单状态
    order_status TINYINT NOT NULL DEFAULT 0 COMMENT '订单状态：0-待支付 1-已支付 2-已发货 3-已完成 4-已取消',
    pay_status TINYINT NOT NULL DEFAULT 0 COMMENT '支付状态：0-未支付 1-已支付 2-退款中 3-已退款',
    
    -- 支付信息
    pay_type TINYINT COMMENT '支付方式：1-微信 2-支付宝 3-银行卡',
    pay_time DATETIME COMMENT '支付时间',
    pay_no VARCHAR(100) COMMENT '支付流水号',
    
    -- 物流信息
    ship_no VARCHAR(100) COMMENT '物流单号',
    ship_company VARCHAR(50) COMMENT '物流公司',
    ship_time DATETIME COMMENT '发货时间',
    receive_time DATETIME COMMENT '收货时间',
    
    -- 收货信息（冗余存储，避免关联查询）
    receiver_name VARCHAR(50) NOT NULL COMMENT '收货人姓名',
    receiver_phone VARCHAR(20) NOT NULL COMMENT '收货人电话',
    receiver_province VARCHAR(50) COMMENT '省',
    receiver_city VARCHAR(50) COMMENT '市',
    receiver_district VARCHAR(50) COMMENT '区',
    receiver_address VARCHAR(255) COMMENT '详细地址',
    
    -- 扩展信息
    user_remark VARCHAR(255) COMMENT '用户留言',
    admin_remark VARCHAR(255) COMMENT '管理员备注',
    extra_data JSON COMMENT '扩展数据',
    
    -- 时间戳
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    deleted_at DATETIME COMMENT '删除时间',
    
    -- 索引
    UNIQUE INDEX uk_order_no (order_no),
    INDEX idx_user_id (user_id),
    INDEX idx_user_status (user_id, order_status),
    INDEX idx_pay_status (pay_status),
    INDEX idx_created_at (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单表';
```

**设计亮点：**
1. 金额全部用 DECIMAL
2. 状态字段详细说明
3. 收货信息冗余（减少 JOIN）
4. 完善的索引设计
5. 预留扩展字段
6. 详细的注释

## 🎯 总结：数据库设计检查清单

### 设计完成后，问自己这些问题：

#### 命名规范
- [ ] 表名是否用复数？
- [ ] 字段名是否见名知意？
- [ ] 是否避免了拼音和缩写？
- [ ] 是否避免了保留字？

#### 字段设计
- [ ] 字段长度是否合理？
- [ ] 金额是否用 DECIMAL？
- [ ] 时间是否用 DATETIME？
- [ ] 是否添加了 created_at、updated_at？
- [ ] 是否有逻辑删除字段？

#### 索引设计
- [ ] 主键是否有索引？
- [ ] 外键是否有索引？
- [ ] 高频查询字段是否有索引？
- [ ] 是否需要联合索引？
- [ ] 索引是否过多？

#### 约束规范
- [ ] 必填字段是否 NOT NULL？
- [ ] 是否有合理的默认值？
- [ ] 唯一字段是否 UNIQUE？
- [ ] 是否需要外键约束？

#### 扩展性
- [ ] 是否预留扩展字段？
- [ ] 是否考虑分库分表？
- [ ] 是否有归档方案？

#### 文档
- [ ] 每个字段是否有注释？
- [ ] 枚举值是否说明？
- [ ] 表是否有注释？

## 💡 最后的话

**数据库设计的三个境界：**

1. **第一层：能用就行**
   - 功能实现就好，管他什么设计
   
2. **第二层：规范设计**
   - 遵循所有规范，不敢越雷池一步
   
3. **第三层：恰到好处**
   - 理解规范背后的原因
   - 知道什么时候该遵守，什么时候可以变通
   - 平衡性能、可维护性和开发效率

**记住：**

> 最好的设计不是最完美的设计，而是最适合你当前场景的设计。
> 
> 小项目不要过度设计，大项目不要偷懒。
> 
> 设计是迭代出来的，不是一次性想出来的。

**保持学习，持续改进！** 🚀
